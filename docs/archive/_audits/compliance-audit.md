**P0-1 비로그인 연락처 노출 — ✅ 수정 완료(2026-06-23)**: 백엔드 `toPostDetail(post, agg, includeContacts)` 추가 → `detail()`이 `!!userId`로 게이트(비로그인 시 `contacts: []`). 버튼 노출용 `hasContact: boolean`(연락처 존재 여부, 값 미포함) 신설. 앱: 버튼은 서버 `hasContact`로 노출, 문의하기 탭(=로그인 상태) 시 `getContacts`가 상세를 인증 상태로 재조회해 연락처 획득. 소유자(인증됨)는 상세에 연락처 그대로 와서 편집 프리필 무변경. 검증: 백엔드 tsc 0/jest 291, 앱 tsc 0/jest 581/eslint 0.

**P1-2 작성화면 안전고지 렌더 — ⏭ 의도적 미적용(WONTFIX, 2026-06-23)**: 법정 강제 아님(면책은 약관 제13조4항에 존재). "무조건 노출해야 하는 순간"인 **연락 시점(문의하기 바텀시트)에는 이미 `ContactSafetyNotice` 노출**됨 — 사기 위험이 실제 발생하는 유일한 고가치 지점. 작성 화면 추가 노출은 중복 + UX 노이즈라 미적용. UI 고지 최소화 원칙.

**P1-3 본문 연락처/금액 — ✅ 부분 적용(2026-06-23)**: 전화번호 본문 차단은 미적용(게시자 본인 연락처 자발 게시 + 구조적 노출은 P0-1에서 차단 → 본문 차단은 과함). 금액(책임비)은 AI 모더레이션 사각(OpenAI Moderation은 혐오·성·폭력·불법만, 금전·거래 미탐지)이라 **개인입양 작성 폼 연락처 섹션에 무상 원칙 안내(`FreeAdoptionNotice`) 정적 노출**로 보완. `SafetyNotice` 제네릭 추출(ContactSafetyNotice 재사용).

**모더레이션 차단 사유 UI 노출 — ✅ 수정 완료(2026-06-23)**: 기존엔 모더레이션 차단 시 앱이 일반 실패 토스트만 표시(서버 사유 폐기). `getModerationMessage(error)` 헬퍼로 `CONTENT_MODERATION` 응답 메시지를 추출해 토스트로 노출. 작성·수정·댓글 6개 mutation(post/qna create·update, comment create·update) 적용. 검증: 앱 tsc 0/jest 584/eslint 0.

**P1-7 Sentry 리플레이 마스킹 — ✅ 수정 완료(2026-06-23)**: `_layout.tsx`의 `mobileReplayIntegration()`을 `{ maskAllText: true, maskAllImages: true, maskAllVectors: true }`로 명시 고정(@sentry/react-native 7.2.0). SDK 기본값 의존 제거 → 버전 변경 시 마스킹 회귀 방지, privacy.md 보장과 코드 일치. tsc 0/eslint 0.

**P1-5 이의제기 딥링크 — ⏭ 재정의(BP 조사, 2026-06-23)**: BP([getstream](https://getstream.io/blog/moderation-appeals-transparency/)·Reddit·Snap)는 "이의 폼 자동 인계"가 아니라 ① 사유 구체 통지 ② 통지문 안에 이의 방법 명시 ③ 이의 채널 제공. keeper는 알림 본문에 "이의가 있다면 문의해주세요" + 1:1 문의(이의제기 유형) 채널을 이미 갖춤 → 딥링크 신설은 BP 필수 아님(보너스). 실 개선 여지는 listener 고정 통지 문구의 **사유 구체화**(별도 결정).

**P1-6 신고큐 BAN — ✅ 수정 완료(2026-06-24)**: 신고 처리 액션에 `BAN` 추가. BAN = 작성자 정지(`UserService.updateStatus`, 마스터·본인 보호 내장) + 콘텐츠 블라인드(`handledAction: BAN`). 정지 검증을 먼저 수행해 실패 시 콘텐츠 미변경. 통지: 정지 알림(ACCOUNT_SUSPENDED)이 작성자 통지를 대신하므로 listener에서 BAN은 작성자 통지 스킵, 신고자 통지는 유지. 백엔드: UserModule export + CommunityModule import, tsc 0/jest 293(+2 BAN). 어드민: 신고 액션바에 "작성자 정지" 다이얼로그(기간·사유), tsc 0/eslint 0.

**전 항목 처리 완료** — 정책 P0/P1 중 코드 보류 항목 없음(P1-2·P1-5는 BP 근거 의도적 미적용).

## P0 — 출시 전 필수

### P0-1. 비로그인 상세 API가 게시자 연락처 노출 🔴 (검증 완료)

- **현상**: `GET /community/posts/:id`(`post.controller.ts:75 @Public`)가 비로그인 포함 누구에게나 호출 가능. `post.service.ts:detail()`이 `toPostDetail(post, ...)`을 **user 유무와 무관하게** 호출 → 응답에 `contacts`(전화/이메일/SNS) 포함(`post.converter.ts:192`). 앱의 "문의하기 게이팅"은 UI 뿐이며 연락처 데이터는 이미 응답에 실려 옴(`contact-sheet.tsx`는 prop으로 받음, 별도 인증 fetch 아님).
- **영향**: 개인입양 게시자의 연락처(개인정보)가 인증 없이 API로 무차별 획득 가능. 개인정보 노출 + 개인입양 법규(연락처 노출 차단·접촉 게이팅) 실효성 무력화.
- **조치(안)**: 서버에서 비로그인(또는 비-문의 컨텍스트) 응답에서 `contacts` 제외. 옵션 (a) `detail`에서 `userId` 없으면 contacts 빈 배열, (b) 연락처 전용 인증 게이트 엔드포인트(`GET /community/posts/:id/contacts` JwtAuthGuard) 분리 후 앱 contact-sheet가 탭 시 호출. (b)가 게이팅 의도에 가장 정합.

## P1 — 출시 전 권장

### P1-1. 동의 버전 미동기화 (검증 완료)

- 앱 상수 `TERMS/PRIVACY/COMMUNITY_POLICY_VERSION = 'v1.0'`(`agreement.ts:1-3`) vs 실제 문서 **terms 1.2 / privacy 1.3 / community 버전없음(시행일자만)**. 사용자가 동의·DB 기록(`agreedTermsVersion` 등)하는 버전과 실제 본 문서가 불일치 → 동의 이력 증빙력 약화.
- **조치(안)**: 앱 상수를 문서 버전과 일치(`'1.2'`/`'1.3'`)시키고, community.md에 버전 표기 추가. 버전 변경 시 재동의 트리거 정책 수립.

### P1-2. 작성 화면 안전·면책 고지 미렌더

- `ContactSafetyNotice` 컴포넌트는 존재하나 작성 화면(`community-write.tsx`/`community-adopt-form.tsx`)에 미삽입. 상세도 문의시트 안에만 노출(상시 X).
- **조치(안)**: 작성 화면 + 상세 상단에 ContactSafetyNotice 렌더(컴포넌트 재활용, 삽입만).

### P1-3. 본문 자유텍스트 연락처/금액 직접입력 차단 없음

- 게이팅 구조는 있으나 본문에 직접 전화번호·금액 입력 시 우회 가능.
- **조치(안)**: 작성 제출 시 정규식 경고/차단(앱+백엔드). 무상 원칙·연락처 게이팅 정합.

### P1-4. 전자상거래법 통신판매중개자 고지 위치

- "당사자 아님" 고지가 이용약관 제13조4항엔 있으나, 개인정보방침(`privacy.md:73`)에는 "통신판매업자" 표현 혼재.
- **조치(안)**: 약관 제13조4항을 1차 근거로 유지, privacy.md 표현 정정.

### P1-5. 블라인드/정지 알림 → 이의제기 딥링크 부재

- `CONTENT_BLINDED`/`REPORT_RESOLVED_*`/`ACCOUNT_SUSPENDED` 알림에 `refType/refId` 없어 탭해도 이동 안 됨(`deeplink.ts:22-37`은 post/comment/inquiry만). 게시자는 body 텍스트만 보고 수동으로 문의 이동. §44-2 통지의 실효성 직결.
- **조치(안)**: 딥링크에 appeal 라우팅 추가 + 문의 화면 컨텍스트 prefill(어느 게시물·조치).

### P1-6. 신고 큐에서 BAN(계정 정지) 미배선

- 신고 처리 액션 = `HIDE|DELETE|NONE`만(`admin-report.dto.ts`). enum엔 `BAN` 존재하나 신고 큐에서 계정 정지 경로 없음 → 운영자가 별도 사용자 화면으로 이동해야 함.
- **조치(안)**: 신고 처리 액션바에 BAN 추가 → user.updateStatus 연계(운영 편의, 법규 위반 아님).

### P1-7. Sentry 리플레이 마스킹 SDK 기본값 의존

- `mobileReplayIntegration()` 인자 없이 호출 → 기본값(maskAllText/maskAllImages) 의존. privacy.md는 마스킹을 보장 표기.
- **조치(안)**: 마스킹 옵션 명시적 pin(SDK 버전 변경 회귀 방지).

### P1-8. 푸시 "시행 시" 조건부 표현

- privacy.md §9-1이 푸시 토큰·알림을 "알림 기능 시행 시" 조건부 표기. 그러나 푸시가 실제 구현·전송됨(`use-register-push-token.tsx`).
- **조치(안)**: 알림 출시 빌드 시점에 "시행" 상태로 문서 전환.

## ✅ 충족 확인(위반 없음)

- **§44-2**: 게시판 공시 미구현이나 약관 제10조의2(임시조치 30일 + 통지 곤란 시 "서비스 내 게시 갈음")로 보완. 자체관리형 운영정책으로 방어 가능.
- **통지 비대칭**: 게시자=사유+이의 유도, 신고자=결과만(`notification.listener.ts:37,59`). 약관 정합.

- **탈퇴·§21-2**: 가입·탈퇴 2탭 대칭, hard delete + PostContact 삭제 + 재식별불가, 정지 안내.
- **정책 3종**: terms/privacy/community 존재·핵심 조항 충실, 4필수 동의 + 버전 저장, 가입·설정 양쪽 노출.
- **위치정보**: 기기 내 처리·서버 미전송, 약관/방침 일치.
