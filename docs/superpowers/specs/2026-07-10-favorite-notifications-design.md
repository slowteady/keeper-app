# 관심 대상 알림 확장 설계 (#1~#3)

작성일: 2026-07-10 / 상태: #1 확정, #2·#3 방향만 합의(세부 미정)

## 문제

keeper의 목표는 "한 마리라도 더 가족을 만나게" 하는 것이고, 그 마지막 관문은 사용자가 보호소에 전화하는 것이다(`shelter_contact_clicked`). 지금 알림 9종은 전부 커뮤니티 상호작용·운영(신고·문의·정지)에 묶여 있고, **입양 연결로 직접 이어지는 알림이 하나도 없다.**

관심 표시한 공고가 마감되어도, 관심 보호소에 새 아이가 들어와도, 그 아이가 입양되거나 안락사되어도 사용자는 모른다.

### 대상 조회

`AbandonmentFavorite` ⋈ `Abandonment` where `processState = 보호중` and `noticeEdt - today ∈ {5, 1}`.
사용자별로 묶어 1건이면 개별 알림, 2건 이상이면 요약 알림.

### 문구

| 상황      | 제목                             | 본문                                    |
| --------- | -------------------------------- | --------------------------------------- |
| 1건 · D-1 | 내일 공고가 끝나요               | 관심 있는 아이의 공고가 내일 마감돼요   |
| 1건 · D-5 | 공고 마감 5일 전이에요           | 5일 후 공고가 끝나요                    |
| 다건      | 관심 있는 공고 N건이 곧 마감돼요 | 가장 빠른 마감은 {내일 \| 5일 후}이에요 |

다건 본문의 "가장 빠른 마감"은 동적으로 채운다. D-1이 섞여 있으면 "내일", 전부 D-5면 "5일 후". 제목만으로는 N건 중 하나가 내일 끝난다는 것을 알 수 없어 사용자가 미룬다.

문구 길이 기준(BP): iOS는 제목 40자·본문 100자 이하, Android 축소 뷰는 제목 40~~50자·본문 40~~90자만 보인다. 사용자가 확실히 보는 것은 **제목과 본문 첫 줄뿐**이므로 본문을 도입부로 낭비하지 않는다. 위 문구는 모두 안전권.

**"찜"이라는 단어를 쓰지 않는다.** 물건을 세는 말이다. 아이에게는 "관심 있는", 공고에는 "N건"을 쓴다.

`imageUrl`은 인앱 목록 표시용으로 계속 채운다(푸시에는 실리지 않는다).

### 시간대 함정

NestJS `@Cron`은 서버 타임존을 따른다. Railway는 UTC이므로 `@Cron('0 10 * * *')`는 **KST 저녁 7시**에 돈다. 반드시 `{ timeZone: 'Asia/Seoul' }`을 명시한다. 기존 크론들이 이걸 지키고 있는지 구현 시 확인할 것.

## 유저 설정

`NotificationCategory`에 `FAVORITE` 하나 추가. 라벨 "관심 공고·보호소", 설명 "관심 있는 공고의 마감·상태 변화, 관심 보호소의 새 공고 알림을 받아요". `section: 'general'`.

#1·#2·#3이 전부 이 카테고리를 공유한다. 셋 다 "내가 관심 표시한 대상에 무슨 일이 생겼다"로 성격이 같고, 알림마다 토글을 만들면 설정 화면이 늘어진다.

"D-5만 받기" 같은 세분화는 하지 않는다. 두 번뿐인 알림을 반으로 가르는 설정은 아무도 쓰지 않는다.

## 반드시 지킬 원칙 (BP 조사에서 도출)

### 1. `FAVORITE`은 명시적 관심 대상 전용

정보통신망법은 **"영리목적의 광고성 정보"**에만 사전 동의를 요구하고, **"수신자와의 거래 관계로 인해 반드시 전달이 필요한 정보"**는 예외다. 사용자가 직접 관심 표시한 대상의 상태 변화는 이 예외에 해당한다. keeper는 입양 중개 수수료가 없어 영리목적 자체가 없다.

**추천·발견 계열 알림(관심 표시하지 않은 공고 추천 등)을 이 카테고리에 섞으면 안 된다.** 광고성으로 분류되는 순간 별도 수신 동의 + 밤 9시~아침 8시 발송 금지 + 2년마다 수신 동의 재확인 의무가 붙는다.

### 2. 새 카테고리는 기존 사용자에게 자동 ON이 된다

`isPushAllowed`가 레코드 없으면 `true`를 반환하므로, 카테고리를 추가하는 것만으로 전 사용자에게 켜진다. **이번 건은 의도한 결과다** — 사용자가 직접 관심 표시한 대상에만, 되돌릴 수 없는 시한을 알리는 트랜잭셔널 알림이므로.

**다음에 카테고리를 추가할 때는 이 동작을 다시 판단해야 한다.** 특히 추천·마케팅 계열이면 기본 OFF가 맞고, 그러려면 `isPushAllowed`의 기본값 자체를 바꾸거나 카테고리별 기본값을 두어야 한다.

### 3. 알림을 늘릴 때 카테고리를 함께 늘리지 않는다

과도한 세분화는 설정 목록을 길게 만들어 사용자가 읽지 않게 한다. 반대로 카테고리가 아예 없으면 "전체 푸시 끄기"로 직행한다. 성격이 같은 알림은 기존 카테고리에 붙인다.

### 4. 운영 파라미터는 코드 상수로 둔다

D-5·D-1과 오전 10시는 환경마다 달라야 할 값이 아니고, 재배포 없이 바꿔야 할 만큼 급하지도 않다. `app_config`(점검 모드·최소 버전)는 **장애 시 즉시 눌러야 하는 스위치**의 자리라 성격이 다르다. 무엇보다 `CHIP_THRESHOLD_DAYS = 5`가 이미 앱 상수로 있어, 백엔드만 DB로 빼면 두 값이 조용히 어긋난다.

실제로 튜닝이 잦아지면 그때 옮긴다.

## #2 관심 보호소 신규 공고 (확정·구현 완료)

`ShelterFavorite`(careRegNo) ⋈ 신규 `Abandonment`(careRegNo). 테이블·연결키는 이미 있었고, `Abandonment.createdAt`과 `(careRegNo, createdAt)` 인덱스만 추가했다.

"신규"의 기준은 `noticeSdt`(공고 시작일)가 아니라 **우리 DB에 레코드가 처음 꽂힌 시각**이다. 공공 API는 공고일과 실제 노출 시점이 하루 이상 어긋나는 일이 잦아, 공고일 기준으로 잡으면 알림이 조용히 누락된다.

- **발송 시각**: KST 10시. `abandonment-sync`가 KST 09시·21시에 도는데, 24시간 롤링 창(어제 10시 ~ 오늘 10시)으로 잡으면 어제 21시분과 오늘 09시분이 정확히 한 번씩만 잡힌다.
- **묶음 규칙**: 사용자당 하루 1건. 신규 공고가 뜬 관심 보호소가 한 곳이면 그 보호소 상세로, 여러 곳이면 요약 1건으로 묶어 관심 목록의 보호소 탭으로 보낸다.
- **상한**: 공고 수가 20건을 넘으면 "20건 이상"으로 표기. 발송 자체가 사용자당 1건이라 대량 유입도 푸시 1건이다.

### 하루 최대 푸시 2건

#1과 #2는 각각 독립적으로 "그날 이 타입을 이미 보냈는가"만 검사한다. 따라서 마감 임박과 신규 공고가 같은 날 겹치면 **한 사용자가 하루에 푸시 2건**을 받는다. 의도한 동작이다. 성격이 전혀 다른 알림(내가 보던 아이가 사라진다 / 새 아이가 왔다)이라 한 건으로 뭉개면 둘 다 묻힌다. 카테고리 통합 상한은 두지 않는다.

### 발송 스위치 (`app_config.notificationBatchEnabled`)

서버는 `develop` push 시 자동배포되지만 앱은 스토어 심사를 거친다. 그 틈에 크론이 새 `NotificationType`을 쌓으면 **구버전 앱의 알림 목록이 통째로 파싱 실패**한다. 그래서 배치 알림 발송을 `app_config` 플래그로 잠가두고, 앱이 충분히 퍼진 뒤 어드민 콘솔에서 켠다. 기본값은 `false`.

이는 "운영 파라미터는 코드 상수" 원칙(4번)과 어긋나지 않는다. D-5·10시 같은 튜닝 값이 아니라 **장애 시 즉시 눌러야 하는 스위치**이고, `app_config`는 정확히 그 자리다.

앱 쪽에는 재발 방지로 `NotificationListResponseSchema`가 모르는 타입을 목록 전체가 아니라 그 항목만 드롭하도록 고쳤다(드롭 발생 시 `logger.error`로 기록). 다만 이미 배포된 구버전에는 소급되지 않으므로 스위치가 여전히 1차 방어선이다.

## #3 관심 공고 상태 변화 (방향만 합의)

`abandonment-sync.service.ts:151`의 upsert가 지금은 덮어쓰기만 한다. upsert 전에 기존 `processState`를 읽어 diff를 감지해야 한다.

**미결정**: 안락사(`EUTHANIZED`)를 알릴 것인가. 좋은 소식(입양)과 나쁜 소식을 같은 알림 채널로 보내는 것이 맞는가. 문구를 어떻게 가를 것인가. 이건 기술 문제가 아니라 제품 결정이며, 사용자에게 상처를 줄 수 있어 신중히 정해야 한다.

## 이번 범위 밖

**어드민 브로드캐스트 알림**은 별도 설계로 분리한다(#1~#3 완료 후 착수). 이유는 성격과 위험도가 완전히 다르기 때문이다.

- `push.service`에 브로드캐스트 메서드가 없다(`sendToUser` 1:1만 존재)
- 큐 인프라가 없다(BullMQ·Redis 미도입). 전체 발송을 HTTP 요청 하나로 처리하면 타임아웃 + 부분 실패 시 복구 불가
- `PushToken`에 앱 버전이 없다. 버전 타겟팅을 하려면 컬럼 추가 + 앱의 토큰 등록 수정이 필요하고, **소급이 안 된다**(기존 토큰은 재등록해야 채워짐)
- 발송 취소가 불가능하다. 오타 하나가 전 사용자에게 나간다. 안전장치가 설계의 일부여야 한다
- 카테고리를 나눠야 한다: 점검 공지는 끌 수 없어야 하고, 기능 출시 안내는 끌 수 있어야 한다
- `FAVORITE`에 섞으면 안 된다(원칙 1)

`PushToken.appVersion`은 **이번에 넣지 않는다.** #1~#3과 브로드캐스트를 모두 구현한 뒤 한 빌드로 배포하므로, 브로드캐스트 설계 단계에서 앱 수정과 함께 넣으면 된다. 앱을 두 번 배포할 때만 발생하는 소급 문제였다.
