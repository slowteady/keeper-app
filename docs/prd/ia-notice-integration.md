## 0. 개정 (2026-06-15) — 세그먼트 모델로 전환

초안의 "공공+개인을 **한 피드에 섞는(interleave) 단일 피드 + 출처 필터+뱃지 + 정규화 단일 카드**"는 폐기한다.

- **사유**: 보호소·개인 공고는 보유 데이터가 달라(공고기간·구조장소·D-day는 보호소 전용) 한 스크롤에 섞으면 카드가 이질적이고, 정규화로 통일하면 **보호소 카드(변경 금지)** 의 핵심 정보를 깎아야 한다.
- **전환**: 입양 탭 안에서 **출처 세그먼트 [보호소 | 개인]** 로 전환(한 번에 한 출처, 섞지 않음). 같은 탭 내 세그먼트 전환 시 카드 구조 통일이 BP → 개인 카드는 **보호소 `AdoptCard` 재사용**(데이터만 개인용 주입). 세그먼트로 출처가 명확하므로 카드 내 출처 뱃지는 생략.
- **찜=좋아요**: 개인 공고 관심 표시는 기존 좋아요(`post_like`) 재사용. 별도 찜(post_favorite) 신설하지 않음.
- **라우트**: 개인 상세는 `community/[id]` → **`adopt-personal/[id]` 이동**(메뉴 이동에 맞춤).
- 아래 본문(특히 FR-1/FR-2, ADR "출처 구분 UI")은 이 개정으로 갱신됨. 집행 기준 문서는 `docs/design`·`docs/spec`.

## 2. Problem / Why

- **입양 동선 분산**: 입양 의도 사용자가 "입양 찾기"를 하는데 경로가 둘로 쪼개짐 — 공공 공고는 **입양 탭**, 개인입양은 **커뮤니티 탭**. 같은 목적인데 메뉴가 달라 개인입양 공고를 발견하지 못하거나 헷갈린다.
- **커뮤니티 정체성 혼탁**: 소통(입양생활·Q&A) + 공고(개인입양) + 제보(실종분실)가 한 탭에 섞여 "커뮤니티가 뭐 하는 곳인지" 흐림.
- **비용**: 개인입양 공고 노출·입양 성사 기회 손실, 신규 사용자 진입 혼란, 커뮤니티 소통 가치 희석.
- **근거**: keeper IA 근본원리 "진입점 2(공공·유저) → 공고 단일 귀결" (`project_keeper_ia_role`) · `ia-redesign.md` §2.

## 3. Goals / Non-Goals

### Goals

- 입양 탐색을 **입양 탭 한 곳**에서 — 공공 + 개인 공고를 한 동선에서 탐색
- 커뮤니티 = **순수 소통**(입양생활·Q&A)으로 정체성 명확화
- "개인입양 = 공고" 원리를 **프로필까지 일관** (내 글 → 내 공고, 찜 통합)

### Non-Goals

- 입양 처리·거래 중개·자동 매칭 — 역할 경계(탐색 동선 통합이지 거래 통합 아님)
- 입양 가이드/매거진·사용자 간 메시징 — `ia-redesign` **C단계**(후속)
- 입양후기 노출 — **A단계**, 별도 백로그(`03-adoption-review-board`)
- 공공·개인 공고의 **데이터·법적 차이 제거** — 출처 구분·개인입양 법규 게이팅(금액란X·연락처 게이팅·면책)은 그대로 유지
- 하단 탭 5 골격 변경 — 입양 탭 **내부 통합**이지 탭 신설/삭제 아님

## 4. Success Metrics

- **정량**: 개인입양 공고 상세 조회수↑, 개인입양 문의 전환율↑(PostHog 도입 후 퍼널로 측정), 입양 탭 탐색 깊이↑
- **정성**: "개인입양 어디서 보나요?" 류 혼란 문의 감소, 커뮤니티가 소통 위주로 정착
- **가벼운 시그널**: 입양 탭 출처 필터·뱃지 인지/사용률, 개인 공고 카드 탭률

## 5. User Scenarios

### 페르소나

- **입양 희망자**: 공공/개인 구분을 모름. "강아지 입양하고 싶다"로 진입.
- **개인입양 게시자**: 보호 중인 동물을 무상 입양 보내려 글 작성.

### 시나리오 (Given-When-Then)

- Given 입양 희망자가 입양 탭 진입, When 목록을 보면, Then 공공+개인 공고가 **한 피드**에 섞여 나오고 각 카드에 출처 뱃지(보호소/개인)가 보인다.
- Given 개인 공고만 보고 싶을 때, When 출처 필터에서 "개인 공고" 선택, Then 개인 공고만 필터링된다.
- Given 개인 공고 상세 진입, When 문의를 누르면, Then 기존 개인입양 **문의 게이팅** 흐름(연락처 노출 정책)이 그대로 동작한다.
- Given 게시자가 프로필 진입, When "내 공고"를 보면, Then 자기가 올린 개인입양이 "내 글"이 아니라 "내 공고"로 표시된다.
- Given 사용자가 커뮤니티 탭 진입, When 탭을 보면, Then 입양생활·Q&A만 있고 개인입양 공고는 입양 탭으로 옮겨져 있다.

## 6. Functional Requirements

### P0 (MVP)

- **FR-1. 입양 탭 출처 세그먼트 피드 (공고 카드 통일)** — As 입양 희망자, 공공·개인 공고를 입양 탭 한 곳에서 같은 카드 언어로 탐색.
  - AC: 입양 탭 상단 **출처 세그먼트 [보호소 | 개인]** — 한 번에 한 출처(섞지 않음). 기존 보호소 목록 API + 개인 목록 API(`category=ADOPTION_PERSONAL`) 각각 사용.
  - AC: **개인 공고를 보호소 `AdoptCard` 재사용**(데이터만 개인용 주입) — 이미지 · 품종(`specificType`) · 동물 속성 칩(성별·나이·중성화) · 지역 · 등록 경과 · 관심(좋아요) 하트. (성별 라벨·칩 스타일은 보호소 mapper 컨벤션 따름)
  - AC: 커뮤니티 글 카드 요소(작성자·본문·댓글·조회수)는 **입양 목록 카드에서 미사용** (상세에서). 보호소 카드는 **0 변경**.
  - AC: 개인 공고 입양완료 = 카드 딤+뱃지(목록 유지, 입양중 우선 정렬). D-day/공고기간/구조장소는 보호소 전용(개인 카드 미표시).
  - AC: 보호소 세그먼트는 기존 정렬(전체/신규/마감임박)·검색 유지, 개인 세그먼트는 최신순+입양중 우선(필터·텍스트 검색 없음).
- **FR-2. 출처 구분 UI (세그먼트)** — 출처를 세그먼트로 전환.
  - AC: 출처 = **세그먼트 [보호소 | 개인]** 전환. (초안의 "필터+뱃지/세그먼트 탭 아님"은 §0 개정으로 폐기 — 데이터 이질로 한 피드 혼합 부적합)
  - AC: 세그먼트로 출처가 명확하므로 **카드 내 출처 뱃지는 생략**.
- **FR-3. 출처별 상세 분기** — 출처에 맞는 문의 흐름.
  - AC: 공공 → 전화/보호소 문의(기존), 개인 → 문의 게이팅(기존) 그대로
- **FR-4. 커뮤니티 탭 재구성** — 소통만 남김. **(이번 사이클 deferred — "커뮤니티 재구성" 단계로 분리. 공고 스코프 완료 후. 현재 커뮤니티 탭의 개인입양 탭은 잔존)**
  - AC: 커뮤니티 탭에서 개인입양 제거, 입양생활·Q&A만 노출
- **FR-5. 개인입양 글쓰기 진입점 이동** — 입양 맥락에서 작성.
  - AC: 입양 탭 우하단 **FAB**를 주 진입점으로 (현재 커뮤니티 개인입양 FAB 이전). 공공은 사용자가 못 올리므로 FAB는 **"개인 공고 올리기"임을 라벨·진입 화면에서 명확히**
  - AC: 프로필 **"내 공고"**에서도 작성 가능(보조·관리 동선)
  - AC: 커뮤니티 탭의 개인입양 작성 진입 제거 **(이번 사이클 deferred — 커뮤니티 재구성 단계. 입양 탭 FAB는 이번 사이클에 추가됨)**
- **FR-6. 프로필 일관** — 개인입양=공고 원리 반영.
  - AC: 프로필 "내 활동"에서 개인입양을 **"내 공고"**로 표기
  - AC: 찜을 **공고(공공+개인) / 보호소** 구분으로 통합 노출

## 7. Data Model (확정)

**신규 컬럼 없음(예상)** — 기존 `abandonment`(공공) + `PostAdoptionPersonal`(개인) 데이터를 그대로 활용. 통합은 **조회·표현 레이어**에서 수행.

- 출처 구분은 데이터 출처(테이블)로 이미 식별 가능 → 뱃지/필터는 표현 레이어.
- 확정(스키마 변경 유무)은 `/spec`에서 통합 조회 방식 결정 시 재검토.

## 8. Backend Impact

### 통합 조회

- **가장 큰 영향**: 공공 + 개인 공고를 한 피드로 노출하려면 (a) 백엔드 통합 조회 API 신규, 또는 (b) 클라이언트 병합 중 택1. 정렬·페이지네이션·출처 필터 일관성이 핵심 — `/spec`에서 결정.
- 두 소스의 카드 표현 모델(제목/이미지/칩/출처 뱃지) 통일 매퍼 필요.

### 마이그레이션

- **찜(favorite) 일원화 시 신규 필요 가능** — 현재 공공만 찜(favorite), 개인 공고는 좋아요(like)만. 공고 카드 통일에 찜을 개인까지 적용하려면 개인 공고 favorite 테이블/API 신설 → 마이그레이션 발생. 미적용(좋아요 유지/찜 생략) 시 스키마 변경 없음. **`/spec` 결정 의존**.
- 그 외 통합(조회·라우팅·UI)은 스키마 변경 없음 예상.

### 영향 범위

- **라우팅**: 개인 공고 상세·글쓰기 경로 이동 가능성 (`/community/*` → 입양 계열). 공유 URL(`our-keeper.com`) 영향 — §10 Open Issue.
- **모더레이션/마스킹**: 개인 공고 신고·블라인드·탈퇴 익명화 정책 그대로 유지.
- **공고 카드 정규화 갭** (§10 Open Issue): ① 찜 vs 좋아요 일원화 ② D-day/마감임박=공공 전용(개인 미표시) ③ 입양완료 등 상태 표현=개인 공고 상태 모델 확인.

## 9. Rollout Plan (Phase)

### Phase 0: 선행

- 통합 데이터 계약 확정(`/spec`): 공공+개인 통합 조회 방식·정렬 규칙·출처 필터·통일 카드 DTO.

### Phase 1: MVP (P0)

- 입양 탭 통합 피드 + 출처 뱃지·필터 + 출처별 상세 분기 + 커뮤니티 재구성 + 글쓰기 진입점 이동 + 프로필 일관.
- **출시 신호**: 통합 피드에서 양 출처가 정상 노출·필터·상세 분기되고, 커뮤니티/프로필 정합 확인 → 출시.

### Phase 2: 확장 (P1+)

- 실종분실 별도 기능 분리 → 이후 입양후기·가이드(A/C).
