## 1. 데이터 인벤토리 (작업의 출발점)

| 영역     | 보유 데이터                                                              | 빈자리                                       |
| -------- | ------------------------------------------------------------------------ | -------------------------------------------- |
| 유기동물 | `abandonment_v2`, `abandonment_favorite`                                 | 사용자 행동 태그(성격/친화도), 검색조건 저장 |
| 보호소   | `shelter_v2`, `shelter_favorite`                                         | 즐겨찾기 목록 페이지, 보호소 공고 알림       |
| 입양후기 | `adoption_review`, `adoption_review_image`                               | **프론트 노출 0**, 작성자/출처 연결          |
| 커뮤니티 | `post` (3 카테고리), `post_comment`, `post_like`, `post_comment_helpful` | LIFE/QNA 탭 미오픈, 사용자간 메시지          |
| 안전     | `post_report`, `comment_report`, `user_block`                            | **데이터만 쌓고 화면 0**                     |
| 유저     | `user` (social, agreedAt, communityPolicyAgreedAt)                       | 알림 토큰, 본인인증, 평판                    |

**핵심 발견**

- DB·API 는 있는데 UI 가 안 붙은 영역이 많다 (LIFE/QNA, 입양후기, 신고/차단 후속, 즐겨찾기 목록).
- 사용자 ↔ 사용자 연결 데이터는 차단 외 전무. 도메인 확장의 최대 빈자리.

## 2. Tier 1 — 즉시 (1~2 스프린트, 새 DB 컬럼 거의 X)

기존 데이터에 UI 만 붙이는 수준. 보통 사용자가 가장 자주 묻는 "왜 이게 없지?" 항목들.

### F-01. 신고 후속 처리 (사용자 측)

- **현황**: 신고 시 토스트만 표시. 같은 글이 계속 피드에 보임 → "신고해도 변화 없음" 학습효과.
- **무엇**:
  - 신고 즉시 본인 피드·디테일에서 해당 글/댓글 숨김 ("다시 보기" 옵션 제공)
  - 이미 신고한 항목엔 "신고됨" 상태 표시 (`post_report` UK 활용)
  - 운영자 처리 완료 시 알림 (F-06 인프라 필요)
- **데이터**: 기존 `post_report.handledAt / handledAction`, `comment_report` 그대로
- **사용자 가치**: 안전감. 데이터를 보낸 보람.

### F-02. 차단 관리 페이지

- **현황**: 차단 토글만 있고 목록·해제 불가.
- **무엇**:
  - `(untabs)/profile/block` 라우트 신설
  - 차단 사용자 목록 + 해제 토글
  - 클라이언트에서 차단 사용자 글/댓글 필터링 (백엔드 동작 여부 함께 확인)
- **데이터**: 기존 `user_block`. 차단 목록 list API 추가.

### F-03. 내 활동 3탭 (내 글 / 내 댓글 / 좋아요)

- **현황**: 좋아요 페이지만 있음. 내가 쓴 글·댓글 회수 불가.
- **무엇**:
  - `(untabs)/profile/activity` 라우트, 3탭 구성
  - 카드 컴포넌트는 기존 `CommunityAdoptCard` 재활용
  - 글은 카테고리 필터 (ADOPTION_PERSONAL / LIFE / QNA)
- **데이터**: 기존 `post.userId`, `post_comment.userId`. list API 만 추가.

### F-04. 즐겨찾기 목록 페이지 (관심 동물 + 관심 보호소)

- **현황**: 즐겨찾기 토글만 작동, 모아 보기 화면 없음.
- **무엇**:
  - `(untabs)/profile/favorites` — 동물 / 보호소 2탭
  - 보호소는 목록 ↔ 지도 토글
- **데이터**: 기존 `abandonment_favorite`, `shelter_favorite`.

### F-05. 커뮤니티 LIFE / QNA 탭 오픈

- **현황**: 백엔드 schema 다 준비됨. 프론트는 `개인입양` 한 화면만.
- **무엇**:
  - `입양생활(LIFE)` 탭 — 사진 + 키워드 + 입양일자 위주의 글 작성/피드
  - `궁금해요(QNA)` 탭 — 질의응답 게시판
  - 카테고리별 write 분기 폼 widget 신규 작성
- **데이터**: 기존 `post_adoption_life`, `post_qna`.

## 3. Tier 2 — 다음 분기 (재방문·전환 핵심)

알림과 검색. 기능 자체보다 **재방문 동인 + 발견성** 인프라 성격이 강하다.

### F-06. 알림 센터 (인앱 + 푸시 인프라)

- **무엇**:
  - 인앱 알림 목록 화면 + 읽음 처리
  - Expo push token 등록·관리
  - 트리거: 내 글 댓글·답글, 내 댓글 도움됨, 신고 처리 완료 (F-01 연결)
- **데이터 신규**: `notification` (userId, type, payload JSON, readAt, createdAt), `user_push_token`
- **중요도**: ★★★ — F-07/08/11/16 의 공통 인프라. 가장 먼저 깔아야 다음이 가능.

### F-07. 검색조건 저장 → 매칭 즉시 푸시 ★

- **참고**: ペットのおうち (일본) — "希望条件に合うペットの掲載を即時通知"
- **무엇**:
  - 동물 필터 화면에서 "이 조건 저장" → 새 공고 등록 시 매칭되면 푸시
  - 프로필에서 저장된 검색 목록 관리·삭제
- **데이터 신규**: `saved_search` (userId, filterJSON, lastMatchedAt) + 매칭 cron 또는 publish 트리거
- **사용자 가치**: 재방문 최강 트리거. "말티즈 + 서울 + 1-3kg" 같은 좁은 조건 매칭이 가장 강하다.

### F-08. 찜한 동물 상태 변경 푸시

- **무엇**: `abandonment_v2.processState` 변경 감지 → 찜한 사용자에게 알림 ("입양 진행됨 / 입양 완료 / 공고 만료 임박")
- **데이터**: 기존 + F-06 인프라
- **사용자 가치**: 찜 데이터에 라이프 부여. 입양 완료 후기 등 다음 액션 유도.

### F-09. 입양 후기 노출 + 다이어리화

- **현황**: `adoption_review` 테이블·이미지 다 있는데 프론트 어디서도 안 보임.
- **무엇**:
  - 홈 상단 슬라이더 "이 친구처럼 가족이 된 아이들"
  - 동물 상세 하단 "비슷한 입양 사례"
  - 후기 작성 라우트 (`community/review/write`)
  - 입양 신청 완료(F-11) 사용자에게 작성 유도
- **데이터 추가**: `adoption_review.userId`, `adoption_review.source` (보호소 desertionNo 또는 개인입양 postId)
- **사용자 가치**: 입양 전환의 핵심 동기부여 콘텐츠.

### F-10. 통합 검색

- **현황**: 입양만 텍스트 검색. 커뮤니티·보호소 미구현.
- **무엇**:
  - 탭별 검색 (동물 / 커뮤니티 / 보호소)
  - 최근 검색어, 인기 키워드 (트렌드 지표)
- **데이터 신규**: `search_log`. 검색 인덱스(MySQL FULLTEXT 또는 별도) 검토.

## 4. Tier 3 — keeper 의 진짜 차별화 (도메인 도약)

포인핸드/공공시스템과 동일한 영역과 겹치지 않고, **사용자 ↔ 사용자 직접 입양 + 임시보호** 라는 사회적 빈자리를 메우는 축.

> **포인핸드 분석 보충 (2026-05-19 추가)**: 포인핸드는 정보 플랫폼이며 입양 신청은 **앱 밖**(보호소 전화 → 직접 방문 → 현장 신청서 작성 → 직원 상담 → 보호소가 입양자 결정) 에서 일어난다. 직영 입양문화센터(마포)도 오프라인 방문 모델. 즉 **인앱 신청 funnel 자체가 1위 서비스가 안 채운 빈자리**이며, 이것이 keeper 의 가장 명확한 차별화 영역이다. ([근거](https://royalpanion.com/magazine/?bmode=view&idx=20394645), [근거](https://bigissue.kr/magazine/new/348/2899))

### F-11. 입양 신청 폼 + 상태 추적 ★

- **참고**: Adopt-a-Pet Rehome — Apply Now → 인앱 신청서 → 주인 검토 → 승인
- **포인핸드 GAP**: 포인핸드는 신청서 작성·검토·상태 추적이 모두 오프라인. keeper 가 채울 빈자리.
- **무엇**:
  - 동물 상세 / 개인입양 글 상세에 "입양 신청" CTA
  - 신청 폼: 자기소개 / 주거환경 / 가족구성 / 반려 경험 / 메시지
  - 글 작성자(또는 보호소)가 신청 목록 확인 → 상태 변경 (대기/연락받음/방문약속/입양완료/거절)
  - 신청자는 "내 입양 신청" 페이지에서 단계 추적
  - F-06 알림 연동 (상태 변경 시 푸시)
- **데이터 신규**: `adoption_application` (userId, targetType, targetId, status, applicantInfo JSON, message), `application_status_log`
- **중요도**: ★★★ — keeper 가 단순 카탈로그 앱이 될지, 입양 funnel 플랫폼이 될지 결정하는 분기점.
- **리스크**: 보호소들이 자체 양식·전화 절차를 고수하는 도메인 관성. 진입장벽이자 기회. 초기엔 개인입양(`ADOPTION_PERSONAL`) 부터 적용해 검증한 뒤 보호소로 확장하는 게 현실적.

### F-12. 단계별 인라인 안전 가이드 ★

- **참고**: Adopt-a-Pet Rehome 의 in-line tips ("전화 통화 시 확인할 것" → "첫 만남 장소 안전 팁" → "최종 입양 서류")
- **무엇**:
  - F-11 의 각 상태 전환 시점에 단계 별 가이드 콘텐츠 표시
  - 콘텐츠는 동물자유연대·카라 절차를 디지털 친화 UX 로 정리
- **데이터**: 콘텐츠 CMS (정적 markdown 또는 DB)
- **사용자 가치**: 직접 입양의 "안전 문제" 라는 본질적 우려를 해결.

### F-13. 임시보호 매칭 + 입양 전환 funnel

- **참고**: BorrowMyDoggy — 단기 돌봄 매칭 모델
- **무엇**:
  - 현재 `protectionType: TEMPORARY` 항목을 매칭 가능 형태로 노출
  - "임시보호 가능" 사용자 등록 → 신청서 흐름은 F-11 재활용
  - 임시보호 종료 시점 "입양으로 전환" CTA
- **데이터 신규**: F-11 의 `adoption_application` 에 `applicationType` 컬럼 추가 (`ADOPTION` / `TEMPORARY_CARE`)
- **사용자 가치**: 무작정 입양보다 임보 거친 사용자의 입양 전환율이 더 높다는 도메인 가설.

### F-14. 본인인증 / 가벼운 평판

- **무엇**:
  - F-11/13 사용자 대상 본인인증 (휴대폰 또는 사회로그인 verified 필드 활용)
  - 사용자 프로필에 누적 입양 / 임보 / 후기 / 도움말 카운트만 노출 (점수·레벨 X)
- **데이터 신규**: `user_verification` (userId, method, verifiedAt). 카운트는 집계 쿼리.
- **사용자 가치**: 직접 입양·임보의 신뢰 인프라. 게임화 없이 자연 신뢰 신호만.

## 5. Tier 4 — 보조·UGC (다른 기능과 함께 자연 발생)

### F-15. 사용자 행동 태그 UGC

- **참고**: WeRescue (60+ 행동 필터)
- **무엇**: 사용자가 보호소·동물 만남 후 태그 부착 — "사람친화", "다묘OK", "분리불안 있음", "산책좋아함" 등. 같은 태그가 N 명 이상 일치하면 동물 상세에 노출.
- **데이터 신규**: `animal_tag` (desertionNo, userId, tag, createdAt)
- **사용자 가치**: 공공데이터에 없는 행동·성격 정보를 커뮤니티가 메움. keeper 만의 차별 데이터 자산.

### F-16. 지역(구·시) 알림

- **무엇**: 사용자가 지역 등록 → 우리 동네 새 공고·새 커뮤니티 글 푸시. F-07 의 변형.
- **데이터**: `user_region` + F-06 인프라 + 보호소 좌표(이미 보유)

## 6. 컷한 기능 (지금은 안 함, 사유 명시)

| ID       | 기능                                             | 컷 사유                                                                                        |
| -------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| **C-01** | AI Visual Search (사진→유사 동물 매칭)           | 비용·기술 부담 + 보호소 사진 품질 들쭉. PMF 잡힌 후 차별화 카드로 보류.                        |
| **C-02** | AI 보조 (신청서 자동 작성 / 동물 태그 자동 생성) | C-01 과 동일 사유. F-11·F-12·F-15 데이터가 쌓인 후 검토.                                       |

| **C-04** | 게임화 (포인트 / 레벨 / 시즌 배지)               | 입양은 진지한 의사결정 — 게임화가 동기를 왜곡할 위험. F-14 "누적 카운트" 로 대체.              |

            │

   ▼        ▼             ▼         ▼
 F-07    F-08           F-11     F-16

## 9. 의사결정이 필요한 큰 질문

1. **방향 축** — 포인핸드는 정보 플랫폼(인앱 신청 funnel 없음, 전화·오프라인 모델). keeper 가 **인앱 입양 신청 funnel** 까지 가져가면 1위 서비스가 안 채운 빈자리를 채울 수 있다. Adopt-a-Pet Rehome 패턴(F-11/F-12) 으로 갈지, 단순 카탈로그(F-01~F-10) 에서 그칠지가 1순위 결정.
2. **보호소 측 인터페이스** — 사용자 일방향 유지 vs 보호소 직접 등록·신청 관리 면 제공. 후자면 도메인 전체가 다시 그려진다.
3. **신고 운영 주체** — `handledAction` 처리 백오피스는 누가? (별도 어드민 웹 / Slack 알림 / 본인 운영)

> **운영 원칙**: keeper 는 비영리 사회공헌 프로젝트. 광고·멤버십·수수료·adopter fee 같은 수익화 옵션은 product 결정 자료에서 제외한다. ([근거: memory/project_keeper_identity.md](../../../.claude/projects/-Users-leeyongmin-Documents-03--------02-keeper-keeper-app/memory/project_keeper_identity.md))
