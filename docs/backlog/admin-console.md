# 운영 콘솔 (Admin Console)

> 작성일: 2026-06-04 · 최종 갱신: 2026-06-19
> 상태: **이번 사이클 P0** (P1 → 승격). 이번 스코프는 **셸 + 문의 답변 슬라이스**로 한정. 나머지 기능(신고·플래그·공지·유저·통계)은 본 문서에 스코프로 남기고 후속 슬라이스로 점진 추가.
> 여러 기능에서 파생되는 admin 요구를 한 곳에 모음. [[release-plan]] §9 "신고 운영 주체" 미결의 귀결점. 운영 인프라 흐름은 [[service-ops-infra]]. 문의 기능은 [[inquiry-support]].

---

## 1. 배경 / Why

- keeper는 1인·소수 운영. UGC(커뮤니티·개인입양 공고·댓글·문의)를 받는 순간 운영자 처리 수단이 필요.
- 현재 백엔드 RBAC 인프라(`UserRole USER/ADMIN` + `@Roles` + `RolesGuard`)는 완비됐고, **문의(inquiry) admin API 3개(목록·답변·상태변경)도 이미 구현**됐으나 **운영자가 쓸 화면이 0** → 문의 피드백 루프가 안 닫힘.
- 신고·모더레이션·운영플래그·공지·유저는 **DB 스키마는 다 있는데 admin API·화면이 전부 비어 있음**.
- 따라서 admin 콘솔을 이번 P0로 승격하되, **셸을 한 번 세우고 첫 슬라이스(문의 답변)만 완성**해 루프를 닫는다. 나머지는 같은 셸 위에 점진 확장.

---

## 2. 형태 (결정)

- **조작 = 별도 웹 콘솔.** keeper-web(our-keeper.com)은 정적 랜딩/약관이라 인증 admin 부적합 → **독립 웹앱**.
- **실시간 인지 = keeper 앱 push.** 운영자(앱 로그인된 소셜 유저)의 폰으로 "새 문의 도착" 등 운영 이벤트 push. _조작은 웹, 인지는 앱_ 채널 분리.
  - 앱 push는 **알림 시스템([[00-notification-system]], 별도 P0) 의존**. 답변 기능은 알림 없이도 동작하고, 알림 시스템 완성 시 "새 문의 → 운영자 push"를 얹는다.
- **두 층 구조**: 셸(한 번) + 기능별 슬라이스(점진).
  ```
  [셸 — 한 번만]  운영자 인증·라우팅·배포·RBAC 연동·공통 목록/상세/폼
        ├─ 문의 답변   (이번 P0 — DB✅ API✅)
        ├─ 신고 처리   (후속 — DB✅ API❌ / 법적 필수)
        ├─ 운영 플래그 (후속 — DB✅ API❌ / 그 전엔 Prisma Studio)
        ├─ 공지 CRUD   (후속 — DB✅ API❌)
        ├─ 유저 관리   (후속 — role 부여 GUI 등)
        └─ 통계        (후순위 — DB❌)
  ```

## 3. 스택 (결정)

- **react-admin** (별도 웹앱, MIT 무료).
  - 사유: **속도 우선** — `dataProvider`(REST 연동) + `authProvider`(로그인) + resource 선언만으로 목록·상세·폼 **화면 자동 생성**. 기존 NestJS REST/JWT에 어댑터로 연동. 레이아웃 반응형 자동(사이드바→드로어), 모바일 목록은 `useMediaQuery`로 `SimpleList` 전환(공식 패턴 1블록).
  - 양보점: MUI(Material UI) 룩 고정 → 디자인이 머티리얼에 갇힘. **내부 운영툴이라 영향 작음**, MUI 테마(색·폰트)로 완화.
  - 재검토 시점: admin이 신고·통계까지 커져 UI 완성도가 중요해지면 **Refine+shadcn/ui** 또는 **자체 Next.js+shadcn**로 갈아탈 수 있음(내부툴이라 교체 리스크가 사용자 앱보다 작음).
- 배포: 독립 앱(Vercel 등). dev 분리는 셸 설계 단계에서 결정.

## 4. 인증·권한 (결정)

- **인증 = 웹 카카오 OAuth + 기존 JWT 재사용.**
  - 운영자 = **오너(본인)가 승격시킨 기존 소셜 유저**. 협력자가 카카오로 로그인 → 오너가 그 계정에 role 부여 → admin 접근.
  - 웹 카카오 OAuth 콜백(인가코드→토큰→검증→keeper JWT 발급) 1개 추가. 백엔드 카카오 검증 로직 재사용. (Google도 가능하나 KR 운영자엔 카카오가 보편적. Apple 웹은 번거로워 제외.)
  - 보호 라우트(UX 차단) + **서버 role 재검증**(`RolesGuard`가 DB에서 role 재조회) 이중 구조.
- **권한 = `ADMIN` 단일 (이분법).** 관리자(ADMIN)이거나, 아예 접속 불가 — 중간 등급(MODERATOR) 없음.
  - 오너·협력자 모두 `ADMIN`으로 승격. 접근 권한이 있으면 전권, 없으면 접근 자체 불가.
  - 모든 admin API는 `@Roles(ADMIN)`. `RolesGuard`가 role 미달 시 차단.
  - 사유: 운영자는 전적으로 신뢰하는 소수만 들임 → 등급 분리 불필요. 단순함 우선. (협력자에게 위험 조작을 제한할 필요가 생기면 그때 MODERATOR 재도입.)
  - 권한 부여 수단: 초기엔 오너가 DB에서 직접 `role = ADMIN` 부여(운영자 소수), 후속 "유저 관리" 슬라이스에서 GUI화.

## 6. 우선순위 (슬라이스 순서)

1. **셸 + 문의 답변** — 이번 P0 (API 완비 → 루프 즉시 닫힘)
2. **신고 처리** — 출시 직후 (법적 의무, 단 admin API 신규 필요. 그 전엔 DB 도구 stopgap)
3. **운영 플래그 GUI** — `app_config` 점검/버전 (그 전엔 Prisma Studio)
4. **공지·유저 관리**
5. **통계·큐레이션**

| Prisma Studio (운영자 UI로)    | 개발자 전용 → 비개발자 협력자(B) 요건 미충족. 단 신고·플래그 **stopgap**으로는 활용                                                                |
| 앱 내 운영자 화면(전부 앱에서) | 문의엔 가능하나 신고 대량 목록·통계 등 데이터 무거운 운영에 모바일 화면이 부적합. 조작은 웹으로                                                    |
| admin 전용 이메일+비번 인증    | keeper엔 비번 개념이 없어(소셜 전용) 비번 저장·재설정 등 인증 시스템을 새로 지어야 함. "유저 승격" 모델과도 어긋남 → 카카오 OAuth 재사용이 더 단순 |
| Google/Apple 웹 OAuth          | provider 1개면 충분. KR 운영자엔 카카오가 보편적, Apple 웹은 도메인 검증 등 번거로움                                                               |
