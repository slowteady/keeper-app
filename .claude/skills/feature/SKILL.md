# /feature — 새 기능 브레인스토밍

keeper 에서 새 기능을 "있어야 하나? 어떻게 생겼나? 컷할까?" 단계에서 발산·수렴.
산출물은 `docs/backlog/<feature-name>.md`.

## 분리 원칙 — 메인 vs 서브에이전트

기준 한 줄: **사용자와 대화가 필요한가**.

- **메인이 직접** — 사용자 ping-pong / 가치관 판단 / 산출물 확정 (2, 4, 5, 6단계)
- **서브에이전트 위임** — 대량 파일 읽기 / 외부 검색 raw 결과 (1, 3단계)

서브에 던질 때는 **좁은 출력 강제** ("훑고 한 줄로 요약", "표로 2~3행만").
raw 그대로 받으면 컨텍스트 보호 효과 사라짐.

## 절차 (순서대로)

### 1. 사전 컨텍스트 로드 — `feature-researcher` 위임 (mode: context)

발산 전에 keeper 도메인을 머릿속에 박는다. 추측으로 시작하면 이미 있는 기능을
또 제안하거나 컷된 옵션을 다시 끄집어내는 사고가 잦다.

대량 파일 읽기는 메인 컨텍스트 보호 위해 에이전트에 위임.

```
Agent(subagent_type="feature-researcher",
  description="feature 사전 컨텍스트",
  prompt="mode: context

  새 기능 키워드: <사용자가 던진 한 문장>")
```

에이전트가 훑을 영역과 출력 형식(3줄 요약)을 알고 있으므로 메인은 키워드만
던지면 됨.

### 2. superpowers brainstorming 스킬 invoke

발산은 superpowers 의 brainstorming 스킬에 위임한다. 자체적으로 발산
프로토콜을 재구현하지 말 것 — 이미 검증된 흐름이 있음.

`Skill` 으로 `superpowers:brainstorming` 호출 후 그 결과를 가지고 3단계로 진행.
brainstorming 결과 없이 3단계로 건너뛰면 keeper 컨텍스트만 있고 발산이
빈약해진다.

### 3. 레퍼런스 조사 — `feature-researcher` 위임 (mode: reference)

브레인스토밍 산출 아이디어를 외부 사례로 검증한다. 직관으로 BP 단정하면
틀린다 — 비슷한 서비스가 이미 시행착오를 다 거쳤다.

검색 raw 결과가 메인에 들어오면 컨텍스트 낭비. 같은 에이전트에 mode 만 바꿔
던지고 표만 받는다.

```
Agent(subagent_type="feature-researcher",
  description="레퍼런스 BP 조사",
  prompt="mode: reference

  아이디어: <2단계 brainstorming 산출 본문 한 문단>")
```

라이브러리·SDK 도입 검토면 context7 은 메인에서 직접 (좁은 질문이고
사용자 컨펌 흐름이 짧기 때문).

### 4. BP 필터링

조사 결과를 그대로 옮기지 말 것. keeper 정체성·규모·운영 부담을 기준으로 거른다.

- keeper 의 비영리·"거래 아닌 가족 매칭" 정체성과 충돌하면 컷
- 1인/소수 운영에서 유지 불가능한 인프라(예: 24/7 모더레이션, 결제 정산)는 컷
- 사용자 규모(초기 신생)에 안 맞는 무거운 패턴은 컷
- 채택한 BP 옆에는 **인용 + "왜 keeper 에 맞는지" 한 줄** 같이 적는다

### 5. 모호하면 → BP 검색 먼저, 그래도 안 풀리면 사용자 피드백

추측으로 결정 강행 금지. 다만 사용자에게 던지기 전에 **검색으로 풀 수 있는지
먼저 따진다**. 모호한 항목의 대부분은 외부 사례가 이미 답을 가지고 있다.

**먼저 시도**:

- WebSearch — "사용자 X가 Y 기능에서 어떻게 동작하는지" 같은 행동 패턴 질문
- context7 — 라이브러리·SDK·UI 패턴(예: BottomSheet 안 키보드 처리) 같은 기술 질문
- 검색 결과로 BP 1~2개 좁히면 "이 방향이 맞나" 라는 좁은 질문으로 사용자에게 컨펌

**검색해도 안 풀리는 것만** 사용자에게 던진다:

- 정체성·우선순위 같이 keeper 내부 의사결정이 필요한 질문
- 두 BP 가 다 합리적이라 keeper 컨텍스트로만 좁힐 수 있는 선택
- 사용자 가치 가설(이 기능이 진짜 필요한가) 자체에 대한 판단

검색 단계 없이 바로 사용자에게 던지면 사용자가 두 번 일한다 — 본인이 결정해
주고 + 알아보기까지. 검색이 가능한 질문인지부터 자문할 것.

사용자 답이 와야 산출물에 박는다.

### 6. 산출물 작성

`docs/backlog/<feature-name>.md` 신규 파일로 남긴다. 파일명은 kebab-case
(예: `event-curation.md`, `adoption-application.md`).

템플릿은 `references/backlog-template.md` 참조. 채울 때:

- 비어두기보다 "TBD — 사용자 결정 대기" 로 명시
- 레퍼런스 BP 섹션에 출처(서비스명 + URL)와 "왜 keeper 에 맞는지" 한 줄 같이
- "컷한 옵션" 섹션 비우지 말 것 — 검토한 안 중 안 한 것의 사유가 미래 자신에게 정보

작성 끝나면 `docs/backlog/product-roadmap.md` 와 어떻게 연결될지 (Tier 추정,
의존 기능)는 사용자에게 짧게 보고만. **product-roadmap.md 는 직접 수정하지
않는다** — 우선순위 의사결정은 별도 단계.

## 안티패턴 (왜 안 하는지)

- **1·2 단계 스킵 후 바로 산출물**: keeper 컨텍스트 모르면 이미 있는 기능을
  재제안한다. 백로그가 노이즈로 차면 가치가 떨어진다.
- **레퍼런스 없이 직관 BP**: 비슷한 서비스가 이미 답을 가지고 있다. 안 찾으면
  남이 거친 시행착오를 반복한다.
- **모호한 채로 결정 강행**: 잘못된 가정으로 만든 산출물은 나중에 통째로 갈아엎어야
  한다. 묻는 비용 < 갈아엎는 비용.
- **검색 가능한 질문을 사용자에게 던지기**: 사용자가 알아봐줘야 할 의사결정과
  WebSearch/context7 로 풀리는 정보 질문은 다르다. 후자를 던지면 사용자가
  두 번 일한다. 검색이 가능한지 자문 후 던질 것.
- **product-roadmap.md 임의 수정**: 우선순위는 횡단 비교가 필요하다. 한 기능
  발산이 다른 기능 우선순위를 바꿀 권한은 없다.
- **구현 계획·코드 스케치**: 발산 단계에서 구체화하면 옵션이 좁아진다. 구현은
  `/writing-plans` / `/executing-plans` 단계.
